\# Сценарії атрибутів якості (Quality Attribute Scenarios)



Нижче наведено 5 кількісно вимірюваних сценаріїв, що описують реакцію системи на різноманітні події. Кожен сценарій містить 6 обов'язкових елементів (Source, Stimulus, Environment, Artifact, Response, Response Measure)\[cite: 1].



\### Сценарій QAS-1: Performance Efficiency (Capacity)

\*\*Опис:\*\* Обробка високого потоку телеметрії від IoT-трекерів.

\- \*\*Source (Джерело):\*\* IoT-трекери, встановлені на вантажних автомобілях\[cite: 1].

\- \*\*Stimulus (Імпульс):\*\* Одночасне надсилання 10 000 MQTT-повідомлень (GPS-дані, швидкість, рівень палива) на секунду\[cite: 1].

\- \*\*Environment (Середовище):\*\* Пікове навантаження системи (Peak Load)\[cite: 1].

\- \*\*Artifact (Артефакт):\*\* Модуль прийому телеметрії (Telemetry API Gateway / MQTT Broker)\[cite: 1].

\- \*\*Response (Реакція):\*\* Запити успішно приймаються, проходять валідацію, зберігаються в асинхронній черзі подій для подальшого запису в базу даних, а поточні координати оновлюються на дашборді диспетчера\[cite: 1].

\- \*\*Response Measure (Міра реакції):\*\* Затримка обробки (Latency) p95 < 200 ms, відсоток втрачених повідомлень (Data Loss) < 0.1%, використання CPU на нодах < 80%\[cite: 1].



\### Сценарій QAS-2: Reliability (Availability)

\*\*Опис:\*\* Відмовостійкість системи при падінні головного вузла бази даних.

\- \*\*Source (Джерело):\*\* Збій інфраструктури (наприклад, апаратна помилка сервера)\[cite: 1].

\- \*\*Stimulus (Імпульс):\*\* Раптова зупинка головної (Master) ноди бази даних геопозицій\[cite: 1].

\- \*\*Environment (Середовище):\*\* Штрафний режим (Degraded mode) під час стандартного робочого навантаження\[cite: 1].

\- \*\*Artifact (Артефакт):\*\* Кластер бази даних (Database Cluster) та Модуль збереження даних\[cite: 1].

\- \*\*Response (Реакція):\*\* Система моніторингу виявляє збій, автоматично перемикає трафік на репліку (Replica), що стає новим Master-вузлом. Дані від трекерів тимчасово буферизуються в черзі повідомлень до завершення перемикання\[cite: 1].

\- \*\*Response Measure (Міра реакції):\*\* Час автоматичного відновлення (Failover time) < 30 секунд, 0% втрачених GPS-даних, система продовжує працювати без переривання сервісу для кінцевих клієнтів\[cite: 1].



\### Сценарій QAS-3: Security (Authenticity / Confidentiality)

\*\*Опис:\*\* Захист системи від підміни геолокаційних даних (Spoofing-атака).

\- \*\*Source (Джерело):\*\* Зовнішня система / Зловмисник\[cite: 1].

\- \*\*Stimulus (Імпульс):\*\* Спроба неавторизованого підключення або надсилання підроблених GPS-координат із зовнішньої IP-адреси від імені легітимної вантажівки\[cite: 1].

\- \*\*Environment (Середовище):\*\* Стандартний режим роботи (Normal operation)\[cite: 1].

\- \*\*Artifact (Артефакт):\*\* Security Gateway / Сервіс автентифікації IoT-пристроїв\[cite: 1].

\- \*\*Response (Реакція):\*\* Шлюз перевіряє наявність валідного клієнтського сертифіката (mTLS). Виявивши невідповідність, система відхиляє з'єднання, ігнорує пакет даних та генерує алерт про інцидент безпеки для логування\[cite: 1].

\- \*\*Response Measure (Міра реакції):\*\* 100% неавторизованих запитів відхиляється, час відповіді на блокування < 50 ms, сповіщення про загрозу записується в Audit Log протягом 1 секунди\[cite: 1].



\### Сценарій QAS-4: Maintainability (Testability)

\*\*Опис:\*\* Забезпечення тестованості при оновленні алгоритмів логістики.

\- \*\*Source (Джерело):\*\* Команда розробників (Developer)\[cite: 1].

\- \*\*Stimulus (Імпульс):\*\* Впровадження нового, більш складного алгоритму розрахунку ETA (очікуваного часу прибуття), що враховує погодні умови\[cite: 1].

\- \*\*Environment (Середовище):\*\* Середовище розробки та тестування (CI/CD Pipeline)\[cite: 1].

\- \*\*Artifact (Артефакт):\*\* Модуль розрахунку маршрутів (Routing \& ETA Module)\[cite: 1].

\- \*\*Response (Реакція):\*\* Розробник запускає набір автоматизованих тестів. Архітектура дозволяє ізолювати бізнес-логіку розрахунків від зовнішніх API (карт, погоди) за допомогою моків (mocks), забезпечуючи перевірку алгоритму\[cite: 1].

\- \*\*Response Measure (Міра реакції):\*\* Покриття коду нового модуля юніт-тестами > 85%, час виконання всього набору юніт-тестів < 3 хвилин, 0 регресійних помилок\[cite: 1].



\### Сценарій QAS-5: Flexibility (Scalability)

\*\*Опис:\*\* Масштабування сервісу при розширенні автопарку компанії.

\- \*\*Source (Джерело):\*\* Внутрішня система моніторингу навантаження (наприклад, Prometheus)\[cite: 1].

\- \*\*Stimulus (Імпульс):\*\* Підключення додаткових 5000 трекерів призводить до стійкого збільшення використання CPU до 75% протягом понад 2 хвилин\[cite: 1].

\- \*\*Environment (Середовище):\*\* Зростання навантаження під час нормальної роботи (Normal operation transitioning to Overload)\[cite: 1].

\- \*\*Artifact (Артефакт):\*\* Сервіс обробки телеметрії (Telemetry Processing Service)\[cite: 1].

\- \*\*Response (Реакція):\*\* Оркестратор контейнерів (Horizontal Pod Autoscaler) виявляє перевищення порогу метрики та автоматично запускає додаткові інстанси сервісу, розподіляючи вхідні з'єднання через Load Balancer\[cite: 1].

\- \*\*Response Measure (Міра реакції):\*\* Час запуску та готовності нових контейнерів < 40 секунд, утилізація CPU на інстансах стабілізується на рівні 50-60%, відсутність обривів з'єднання під час масштабування\[cite: 1].
