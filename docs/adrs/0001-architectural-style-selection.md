\# ADR-0001. Вибір архітектурного стилю для ядра системи\[cite: 1]



\## Статус\[cite: 1]

Accepted\[cite: 1]



\## Контекст (Context)\[cite: 1]

Розроблювана система "Smart IoT Logistics" має специфічний змішаний профіль навантаження: з одного боку, необхідно безперервно обробляти величезний потік GPS-телеметрії від тисяч трекерів (високе навантаження на запис), з іншого — надавати доступ користувачам до бізнес-сутностей, таких як замовлення, профілі водіїв та налаштування клієнтів (помірне навантаження, складні зв'язки). Обробка телеметрії та бізнес-логіка мають різні вимоги до масштабування та надійності\[cite: 1].



\## Рішення (Decision)\[cite: 1]

Прийнято рішення використовувати \*\*Мікросервісну архітектуру (Microservices)\*\* для розділення потокової обробки IoT-даних та управління бізнес-процесами\[cite: 1].

Ядро системи буде розділено на незалежні сервіси (наприклад, Telemetry Ingestion Service, Routing \& ETA Service, Order Management Service), які взаємодіятимуть через брокер повідомлень (Kafka/RabbitMQ) для асинхронних задач та REST/gRPC для синхронних\[cite: 1].



\## Розглянуті альтернативи (Alternatives Considered)\[cite: 1]

\- \*\*Модульний Моноліт (Modular Monolith):\*\*\[cite: 1]

&#x20; - \*Переваги:\* Простіше розгортання на початковому етапі, легший моніторинг.

&#x20; - \*Недоліки / Чому відхилено:\* Неможливість незалежного масштабування сервісу прийому телеметрії. Якщо модулі логістики впадуть через баг, це може зупинити прийом критичних GPS-даних\[cite: 1].

\- \*\*Serverless (FaaS):\*\*

&#x20; - \*Переваги:\* Ідеальне автомасштабування "з коробки".

&#x20; - \*Недоліки / Чому відхилено:\* Проблема "холодного старту" (Cold Start) та висока вартість при постійному інтенсивному потоці даних (24/7 потік телеметрії від автопарку).



\## Наслідки (Consequences)\[cite: 1]

\- \*\*Позитивні наслідки:\*\*\[cite: 1]

&#x20; - Атрибути якості: Висока масштабованість (Scalability) сервісу телеметрії незалежно від інших модулів\[cite: 1].

&#x20; - Відмовостійкість (Fault Tolerance): Збій у сервісі сповіщень не вплине на прийом GPS-координат.

\- \*\*Негативні наслідки / Компроміси (Trade-offs):\*\*\[cite: 1]

&#x20; - Зростає складність інфраструктури (потрібен Kubernetes або Docker Swarm)\[cite: 1].

&#x20; - Необхідність вирішення проблеми розподілених транзакцій для бізнес-сутностей (використання Saga Pattern)\[cite: 1].
